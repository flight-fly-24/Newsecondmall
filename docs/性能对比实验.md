# 松果集市：单体与微服务性能对比实验

> 文档状态：已完成。三个接口均完成单体版与微服务版测试；所有有效数值均来自对应 JMeter HTML 报告和 JTL 原始文件。

## 1. 实验目的

在相同硬件、相同数据集、相同压测脚本和相同负载参数下，对比以下两个部署形态的接口性能：

- **单体版本**：`shopping_back/shopping_back/` 的 backend 容器服务直连，主机端口为 `18080`。
- **微服务版本**：商品、店铺接口由 catalog-service 服务直连；登录接口由 user-service 服务直连，主机端口均为 `18080`（分时测试）。

本实验关注实际观测到的吞吐量、响应时间、错误率和资源消耗。微服务并不预期一定比单体更快；它可能因网关转发、服务间调用、序列化和网络通信而增加单请求延迟。

## 2. 对比接口与选择理由

| 编号 | 接口 | 类型 | 选择理由 |
|---|---|---|---|
| PERF-CMP-01 | `GET /api/products` | 商品列表查询 | 首页高频读接口，适合比较查询吞吐量与延迟。 |
| PERF-CMP-02 | `GET /api/stores` | 店铺列表查询 | 第二个独立读场景，用于避免只以单一接口得出结论。 |
| PERF-CMP-03 | `POST /api/auth/login` | 用户登录 | 典型写入与鉴权场景，可补充读接口之外的业务性能对比。 |

> 本轮选择 3 个主要接口。登录接口正在按与前两项相同的负载口径补测微服务版。

## 3. 环境与公平性控制

| 项目 | 单体版本 | 微服务版本 | 实际填写 |
|---|---|---|---|
| 代码提交号 | 同一提交或标注差异 | 同一提交或标注差异 | 待填写 |
| 测试机器 | 同一台 | 同一台 | 待填写 CPU、内存、操作系统 |
| Java / JMeter 版本 | Java 17；JMeter 5.6.3 | Java 17；JMeter 5.6.3 | Docker Desktop 本机执行 |
| JMeter 压测机 | 同一 Windows 主机 | 同一 Windows 主机 | JMeter 与被测容器同机 |
| 数据库版本与初始数据 | MySQL 8.4，`shop_db` | MySQL 8.4，`catalog_db` | 商品和店铺数据经字节级核对一致 |
| 访问入口 | `127.0.0.1:18080` | `127.0.0.1:18080` | 服务直连，不含 Nginx 网关；微服务按接口分时映射 catalog-service 或 user-service |
| 服务启动参数 | `-XX:MaxRAMPercentage=75.0` | 默认微服务镜像参数 | 以 Docker Compose 配置为准 |

执行原则：

1. 每轮仅启动待测版本，避免另一版本占用 CPU、内存、端口或数据库连接。
2. 每次压测前恢复相同数据库快照；登录压测产生的 Token、日志和缓存不应影响下一版本。
3. 本次未单独预热；服务冷启动后按 20 → 50 → 100 并发依次执行，并在结论中说明该限制。
4. 两个版本使用完全相同的 JMeter 计划、线程数、爬升时间和持续时间。
5. 每个“版本 × 并发档位”至少执行 3 次，记录平均值；若某次异常，保留证据并说明是否重测，不能静默删除。

### 3.1 本次数据一致性验证

2026-09-02 在本地 Docker 测试环境中，将单体 `shop_db` 的店铺和商品复制到微服务 `catalog_db`。使用 `HEX(shop_db.goods.goods_name)` 与 `HEX(catalog_db.goods.name)` 对商品 ID 1001、1002、1003 进行逐字节核对，结果一致。PowerShell 显示微服务 JSON 时出现乱码，是响应头未显式声明字符集造成的客户端显示现象，不是数据库数据损坏；JMeter 仍以 HTTP 响应字节执行测试。

## 5. 执行步骤

### 5.1 准备

1. 记录本次 Git 提交号：`git rev-parse HEAD`。
2. 初始化或恢复单体、微服务分别使用的等价测试数据；准备可用测试账号。
3. 启动待测版本，确认以下接口均可访问且返回正确业务数据：

   ```powershell
   Invoke-WebRequest http://127.0.0.1:18080/api/products -UseBasicParsing
   Invoke-WebRequest http://127.0.0.1:18080/api/stores -UseBasicParsing
   Invoke-WebRequest http://127.0.0.1:18080/api/auth/login -Method POST -ContentType 'application/json' -Body '{"username":"demo","password":"demo123"}' -UseBasicParsing
   ```

4. 设置 JMeter 安装路径，例如：

   ```powershell
   $env:JMETER_HOME = 'C:\apache-jmeter-5.6.3'
   ```

### 5.2 执行压测

项目已有综合计划 `tests/performance/shop-api-load.jmx` 和执行脚本 `tests/performance/run-jmeter.ps1`。对每个版本、每个负载档位连续执行 3 次；下例为 20 并发、5 分钟：

```powershell
.\tests\performance\run-jmeter.ps1 -HostName 127.0.0.1 -Port 8080 `
  -Threads 20 -RampSeconds 20 -DurationSeconds 300
```

只测商品列表时，可使用 `tests/performance/catalog-api-load.jmx` 对应脚本：

```powershell
.\tests\performance\run-catalog-jmeter.ps1 -HostName 127.0.0.1 -Port 8080 `
  -Threads 20 -RampSeconds 20 -DurationSeconds 300
```

每次完成后保存 `tests/performance/results/<时间戳>/` 下的：

- `result.jtl`：原始采样数据；
- `report/index.html`：JMeter HTML 报告；
- `jmeter.log`：执行日志；
- 服务器/容器 CPU、内存、数据库连接数截图或导出数据。

建议按 `证据/性能对比/<版本>/<并发>/<第几次>/` 归档，避免后一次结果覆盖前一次。

## 8. 实验结论

### 8.1 实验结论

本次在同一 Windows 主机、同一 Docker Desktop/MySQL 环境、相同 JMeter 计划和参数下，完成商品列表、店铺列表和登录三个主要接口、三档并发、每档三次的对比。全部有效运行的错误率均为 0.00%。

商品列表上，微服务三次平均吞吐量在 20、50、100 并发下分别为单体的约 2.2 倍、1.9 倍和 20.9 倍；但 50、100 并发结果存在显著运行间波动，不能据此断言架构本身必然带来同等性能增益。店铺列表上，两种版本差异较小：20 并发单体略高，50、100 并发微服务略高或更高。登录接口上，微服务在 20、50 并发下吞吐量及延迟略优；100 并发下两者接近，单体吞吐量略高、微服务 P95 略高。

### 8.2 差异解释

- 商品列表与店铺列表的微服务请求只经过 catalog-service，登录请求只经过 user-service；均未经过网关或跨服务业务调用，因此反映的是服务拆分后的局部链路，不代表完整端到端微服务调用。
- 店铺列表返回数据量小、查询数据仅 3 个店铺，因此延迟和吞吐量更容易受 JVM、MySQL 缓存及本机后台负载影响。
- 本轮不存在业务错误；一次微服务店铺测试因接口实际返回数组而与旧的 `code:0` 断言不匹配，已修正断言并重跑，该失败批次未计入结果。

### 8.3 有效性与限制

本实验是同机服务直连测试，JMeter 与被测容器共享 CPU、内存和网络；未经过 Nginx/API 网关，也未单独预热。商品接口在连续测试中出现明显升温和运行间波动，故结论仅适用于当前本机、当前数据规模和当前部署参数。已人工查看过 `docker stats`，但未形成覆盖完整压测过程、可计算平均值和峰值的 CPU/内存采样文件，故本轮不比较资源占用。微服务的独立扩容、网关开销、跨服务调用、故障隔离能力仍需通过多实例和端到端实验验证。
