# 微服务接口测试与迁移状态

## 1. 文档目的

本文用于记录 `master` 分支根目录 `services/` 下四个业务微服务的接口迁移、HTTP API 测试、跨服务联调和阻塞状态。

> 测试范围仅包含 `services/user-service`、`services/catalog-service`、`services/trade-service` 和 `services/interaction-service`。`shopping_back/*-service` 下的另一套合入代码不作为本组当前测试对象。

原有 `tests/api/soft-shop-api.postman_collection.json` 继续作为旧单体完整 API 回归基线；微服务测试使用 `tests/api/soft-shop-microservices.postman_collection.json`，两者不能互相覆盖。

## 4. 状态定义

| 状态 | 判定规则 |
|---|---|
| 待迁移 | 新服务中尚无对应接口 |
| 开发中 | 负责人正在迁移，接口契约尚未冻结 |
| 待联调 | 已有实现，但运行环境、依赖或路由尚未完成 |
| 测试中 | 已编写并开始运行 HTTP API 测试 |
| 已通过 | 服务真实运行，HTTP 状态和关键响应断言全部通过并保存报告 |
| 阻塞 | 存在明确的外部前置条件，当前无法继续 |

“代码存在”或“单元测试通过”不能直接标记为“接口已通过”。

## 6. 接口覆盖矩阵

`soft-shop-microservices.postman_collection.json` 由 `tests/api/build-microservices-collection.mjs` 生成，当前包含 76 个请求。覆盖统计以“HTTP 方法 + 路径”为单位，不以 Controller 文件数或页面数代替接口数。

| 服务域 | 已覆盖公开接口 | 内部接口 | 代表性异常路径 | 当前状态 |
|---|---|---|---|---|
| 用户与认证 | 注册、登录、当前用户、资料更新、搜索、用户查询 | 用户和地址快照 | 重复注册、错误密码、伪造 Token、重复基础用户 | 已编写，待真实环境报告确认 |
| 地址与用户中心 | 地址增删改查、设默认；买家/卖家/管理员中心；买卖家实名；实名通过/驳回；互动记录；用户状态、信用、删除 | — | 未登录、角色权限由认证及中心流程覆盖 | 已编写，待真实环境报告确认 |
| 商品与店铺 | 商品列表、我的商品、详情、发布、修改；店铺列表、我的店铺、详情、店铺商品；收藏关系增查清 | 商品快照 | 非法发布参数 | 已编写，待真实环境报告确认 |
| 交易 | 购物车增查改选删；订单创建、列表、详情、评价、取消 | 订单、参与人、卖家汇总 | 未登录购物车 | 已编写，待真实环境报告确认 |
| 互动 | 健康检查；话题增查、详情、关注/取消；帖子增查、评论、点赞、收藏行为 | — | 未登录创建话题 | 已编写，待真实环境报告确认 |

`PUT /internal/products/{id}/sold` 是交易服务在创建订单时触发的有副作用内部接口。Collection 不单独重复调用，而是在“创建订单 → 订单确认 → 商品状态变化”跨服务流程中间接覆盖，避免同一商品被手工提前标记为已售而破坏后续订单测试。

每次 Controller 增删接口后，应同时修改生成器并执行：

```powershell
npm run build:api:microservices
```

生成器是 Collection 的可维护源文件，不应只在生成后的大 JSON 中手工修改。

## 7. API 测试命令及含义

| 命令 | 含义 | 是否自动启动环境 | 报告 |
|---|---|---:|---|
| `npm run test:api` | 兼容旧命令，等价于单体基线测试 | 否 | `tests/api/reports/newman-report.*` |
| `npm run test:api:monolith` | 明确运行改造前单体/统一入口 Collection | 否 | HTML、JUnit XML |
| `npm run test:api:microservices` | 测试已经启动并可从宿主机访问的四微服务 | 否；会等待就绪 | HTML、JUnit XML、JSON、运行元数据 |
| `npm run test:api:microservices:compose` | 创建隔离 Compose 项目，构建并启动四服务，等待就绪、测试、失败采集日志、最后清理 | 是 | HTML、JUnit XML、JSON、运行元数据 |
| `npm run test:api:all` | 先跑单体基线，再跑已经启动的微服务；任一失败立即停止 | 否 | 两套报告 |
| `npm run build:api:microservices` | 从生成器重建微服务 Collection | 不适用 | Collection JSON |

首次使用先安装锁定版本依赖：

```powershell
npm ci
```

### 7.1 推荐：隔离环境全自动测试

```powershell
npm run test:api:microservices:compose
```

该命令使用独立 Compose 项目名 `soft-shop-api-test` 和独立数据卷，不覆盖日常开发环境；通过 `deploy/docker-compose.api-test.yml` 仅向 `127.0.0.1` 暴露 8081～8084。测试结束执行 `down --volumes`。若需要保留失败现场：

```powershell
node tests/api/run-microservices-newman.mjs --start-compose --keep-environment
```

检查结束后手工清理：

```powershell
docker compose --project-name soft-shop-api-test --env-file deploy/.env `
  -f deploy/docker-compose.yml -f deploy/docker-compose.api-test.yml down --volumes --remove-orphans
```

### 7.2 测试已运行的服务

四服务已经通过端口 8081～8084运行时：

```powershell
npm run test:api:microservices
```

测试远程或自定义端口：

```powershell
node tests/api/run-microservices-newman.mjs `
  --user-url=http://host:8081 `
  --catalog-url=http://host:8082 `
  --trade-url=http://host:8083 `
  --interaction-url=http://host:8084
```

运行器在 Newman 前依次检查四服务；默认最长等待 180 秒。任一服务未就绪、任一请求或断言失败，进程均返回非零退出码，可直接作为流水线门禁。

### 7.3 Postman 手工调试

导入：

```text
tests/api/soft-shop-microservices.postman_collection.json
```

服务直连变量默认值：

```text
user_url=http://127.0.0.1:8081
catalog_url=http://127.0.0.1:8082
trade_url=http://127.0.0.1:8083
interaction_url=http://127.0.0.1:8084
```

Collection 自己创建带随机后缀的买家、卖家和一次性用户，保存 Token 与资源 ID，再顺序完成地址、用户中心、商品、店铺、购物车、订单和互动流程。管理员账号由 user-service 启动时初始化为 `admin/admin123`，仅用于隔离测试环境。

### 7.4 直接 Newman（仅用于排错）

四个服务启动后执行：

```powershell
npx newman run .\tests\api\soft-shop-microservices.postman_collection.json `
  --reporters cli,htmlextra,json,junit `
  --reporter-htmlextra-export .\tests\api\reports\microservices\newman-report.html `
  --reporter-json-export .\tests\api\reports\microservices\newman-report.json `
  --reporter-junit-export .\tests\api\reports\microservices\newman-report.xml
```

日常和流水线优先使用 npm 命令，因为运行器额外提供就绪等待、标准报告、Git 提交元数据、失败退出、Compose 诊断和环境清理。直接 Newman 不提供这些保障。

### 7.5 报告与判定

微服务报告固定输出到：

```text
tests/api/reports/microservices/newman-report.html
tests/api/reports/microservices/newman-report.xml
tests/api/reports/microservices/newman-report.json
tests/api/reports/microservices/run-metadata.json
```

- HTML：人工查看、答辩展示。
- JUnit XML：CodeArts/Jenkins 等流水线统计。
- JSON：保留请求、断言和响应时间原始结果。
- `run-metadata.json`：记录 Git 提交、测试时间、四服务 URL、是否使用隔离 Compose 和退出码。

报告目录默认不提交 Git；流水线必须把整个目录打包为构建产物。只有退出码为 0，且 HTML/JSON/XML 与元数据均成功保存，才能标记“已通过”。

## 8. 关键测试流程

### 8.1 全接口回归流程

```text
注册并登录买家、卖家、管理员
→ 用户资料、查询、地址完整 CRUD、三类用户中心和实名审核
→ 商品发布/修改/查询、店铺与收藏关系
→ 购物车完整 CRUD、下单、订单内部查询、评价、取消
→ 话题、关注、帖子、评论、点赞、收藏行为
→ 清理一次性用户和测试资源
```

### 8.2 跨服务订单流程

```text
准备买家 Token
→ 创建在售商品
→ trade-service 调用 user-service 校验当前用户
→ trade-service 调用 catalog-service 获取商品快照
→ trade-service 在 trade_db 创建订单快照
→ catalog-service 幂等标记商品已售
→ 查询订单并校验 CONFIRMED
```

重点断言包括 HTTP 状态、JSON 响应、统一业务码、动态 ID 传递、认证失败、参数校验、冲突结果和跨服务结果。故障注入及幂等并发属于独立故障/集成实验，不用普通全接口 Collection 代替。
