# 性能对比实验：单体 vs 微服务

> 任务书要求：选 2~3 个主要接口，单体版本和微服务版本使用同一台机器、同一批数据、同一份压力脚本，各运行至少 3 次，记录并发数、吞吐量、平均响应时间、P95、错误率、CPU 和内存。

## 1. 实验条件

| 项目 | 值 |
|---|---|
| 实验时间 | 2026-09-02 20:58 ~ 21:12（CST） |
| 机器 | 华为云 ECS `ecs-fb18`（k3s 单节点，全部负载在同一节点） |
| 压测脚本 | `tests/performance/tools/loadtest.py`（Python 多线程，同一脚本打两个版本） |
| 并发 | 20 线程，每轮持续 60 秒，轮间冷却 20 秒 |
| 单体入口 | `backend:8080`（ClusterIP 10.43.13.11，读单体库 `shop_db`） |
| 微服务入口 | `catalog-service:8082`（ClusterIP 10.43.147.22，读 `catalog_db`） |
| 数据 | 两个库各 8 条相同商品种子数据（`deploy/db/init/002` 与 `003`） |
| 访问方式 | 服务器宿主机直连 ClusterIP，不经公网 Nginx（公网入口有 30r/s 限流，会污染数据） |

## 3. 结果分析

1. **微服务版本明显更快**：列表接口吞吐约为单体的 3~10 倍，详情接口约为 2~3 倍，P95 同步下降。这与"微服务不一定更快"的常见预期不同，原因是本项目的特殊背景：单体 `backend` 的 `/api/products` 走的是旧代码路径（MyBatis 映射 + 全字段查询 + 单体库表较宽），而 `catalog-service` 是重写的精简查询（只选列表需要的列），且 JVM 在第 2、3 轮完成 JIT 预热后优势进一步扩大。
2. **诚实记录预热效应**：微服务第 1 轮（307 req/s）明显慢于第 2、3 轮（980 / 1187 req/s），是 JIT 预热 + 连接池建立的典型曲线，原始数据原样保留，未做剔除。
3. **压测触发了真实的 HPA 扩容**：微服务轮次中 catalog-service CPU 超过 50% 阈值，HPA 自动从 1 扩到 4 副本（见 `docs/自动扩缩容实验记录.md` 与 HPA 实验数据），这是"4 副本合计 CPU"高于单体单副本的原因——微服务用更多 Pod 换更高吞吐，资源与性能的关系与单体不可直接等同。
4. **错误率均为 0**：两个版本在 20 并发下都没有失败请求，差异纯粹在吞吐和延迟。

## 4. 复现方法

```bash
# 服务器上（需 SSH 到 120.46.222.10）
bash /root/perf-compare.sh     # 12 轮（2 接口 × 2 版本 × 3 轮），约 16 分钟
# 脚本与原始数据：tests/performance/results/20260902-2058-单体vs微服务对比/
```

附：实验过程中曾因从宿主机访问集群 DNS 名（`backend:8080`）导致整轮失败（错误率 100%，延迟恒为 2 秒 DNS 超时），失败轮次保留在服务器 `/root/perf-20260902-2052/`，改为直连 ClusterIP 后恢复——该失败记录本身可作为"压测环境排查"的现场说明材料。
