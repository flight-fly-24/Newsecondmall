# 松果集市测试方案与用例

> 文档版本：v2.0
>
> 适用系统：松果集市新品与二手商品交易平台
>
> 编写日期：2026-08-25
>
> 文档性质：测试执行依据（测试结果必须以报告、截图或日志为准）

## 1. 测试目标

本轮测试验证系统的功能正确性、接口稳定性、页面业务流程、并发性能、安全性和部署可靠性。测试覆盖前端、后端、MySQL 数据库及前后端之间的调用链路。

## 2. 测试工具与分工

| 工具 | 测试类型 | 主要测试内容 | 输出证据 |
|---|---|---|---|
| Docker / Docker Compose | 部署与环境测试 | 服务构建、容器启动、健康检查、重启恢复、数据持久化 | 容器状态、启动日志、访问截图 |
| JUnit 5 + Mockito | 白箱、单元测试 | 后端服务类的正常、异常和边界分支 | Maven 测试报告 |
| JaCoCo | 白箱覆盖率 | 统计行覆盖率、分支覆盖率和未覆盖代码 | HTML 覆盖率报告 |
| Postman | 黑箱、接口测试 | 接口状态码、响应结构、参数校验、鉴权和权限隔离 | Collection Runner 报告 |
| Selenium | 前端自动化测试 | 用户在浏览器中的完整业务流程 | 执行报告、失败截图 |

## 3. 测试环境

### 3.1 基础环境

| 项目 | 测试配置 |
|---|---|
| 操作系统 | Windows 11 或 Linux 服务器 |
| 前端地址 | `http://127.0.0.1:5173` 或测试服务器地址 |

| 测试账号 | 普通买家、卖家、管理员各一个 |

### 3.2 测试前置要求

1. 前端、后端和 MySQL 均已启动，后端 8080 端口可访问。
2. 测试库包含可展示商品、店铺和测试账号。
3. 测试使用独立环境，不对正式生产数据执行新增、删除、压力或安全扫描。
4. 每轮测试记录代码提交号、测试时间、执行人员和工具版本。
5. 涉及新增、下单、审核、删除的用例执行后恢复测试数据。

### 6.4 Postman 自动断言

每个请求至少检查：HTTP 状态码、响应时间、`Content-Type`、业务码、必要字段和字段类型。登录请求保存 Token 到测试环境变量；需要鉴权的请求统一使用该变量。集合执行时不得只看请求是否发送成功，断言失败即判定用例失败。

## 8. JMeter 性能与压力测试

现有计划文件：`tests/performance/shop-api-load.jmx`，执行脚本：`tests/performance/run-jmeter.ps1`。

### 8.1 接口场景

| 编号 | 性能场景 | 请求 | 校验内容 |
|---|---|---|---|
| PERF-01 | 用户登录 | `POST /api/auth/login` | HTTP 200、Token 提取成功、无业务错误 |
| PERF-02 | 首页商品查询 | `GET /api/products` | HTTP 200、业务码为 0、列表结构正确 |
| PERF-03 | 店铺列表查询 | `GET /api/stores` | HTTP 200、响应结构正确 |
| PERF-04 | 登录后用户中心 | `GET /api/center/buyer` | 携带 Token 后返回 200，不出现越权错误 |

### 8.2 负载模型

| 阶段 | 并发用户 | 持续时间 | 目的 |
|---|---:|---:|---|
| 冒烟 | 1 | 1 分钟 | 验证脚本、参数和断言正确 |
| 基准 | 20 | 5 分钟 | 获取正常负载下的基线数据 |
| 负载 | 50、100 | 每档 10 分钟 | 验证目标并发下的稳定性 |
| 压力 | 从 100 逐步增加 | 每档 5 分钟 | 找到响应恶化或错误明显上升的拐点 |
| 稳定性 | 50 | 30 分钟以上 | 检查内存增长、连接池耗尽和长期错误 |

### 8.3 性能验收标准

| 指标 | 验收标准 |
|---|---:|
| 总错误率 | < 1% |
| 商品、店铺查询 P95 | < 500 ms |
| 登录和用户中心 P95 | < 800 ms |
| 单接口 P99 | < 1500 ms |
| 测试期间后端 CPU 平均使用率 | < 75% |
| 稳定性测试 | 无持续内存增长、服务崩溃、连接池耗尽 |

报告必须记录吞吐量、平均响应时间、P90、P95、P99、最大响应时间、错误率，以及后端 CPU、内存和数据库连接情况。压力测试失败时应保留首次超过阈值的并发数。

## 9. OWASP ZAP 安全测试

| 编号 | 安全场景 | 测试内容 | 预期结果 |
|---|---|---|---|
| SEC-01 | 未授权访问 | 扫描需要登录的用户中心、订单、消息和管理接口 | 未登录请求被拒绝 |
| SEC-02 | 越权访问 | 用普通用户访问管理员接口或他人数据 | 返回 403，敏感数据不泄露 |
| SEC-03 | 输入注入 | 在登录、搜索、发帖和消息参数中使用 SQL/XSS 测试字符串 | 不执行脚本、不改变查询逻辑、不出现数据库错误栈 |
| SEC-04 | 安全响应头 | 检查点击劫持、内容类型、缓存和 CSP 等响应头 | 高风险缺失项修复或形成审核记录 |
| SEC-05 | 敏感信息泄露 | 检查错误响应、日志和前端资源 | 不出现数据库密码、Token、堆栈和内部路径 |
| SEC-06 | 文件上传 | 上传非图片、超大文件和伪造扩展名文件 | 非法文件被拒绝，文件名与路径不可注入 |
| SEC-07 | Token 滥用 | 使用伪造、空白、过期和被修改的 Token | 全部被拒绝 |

ZAP 自动扫描用于发现风险，最终结论需要人工复核，避免把误报直接记为系统缺陷。

## 11. 执行顺序

1. 使用 Docker 部署独立测试环境，确认基础服务可用。
2. 执行 JUnit 单元测试并生成 JaCoCo 覆盖率报告。
3. 使用 Postman 完成接口功能、异常、边界和权限测试。
4. 使用 Selenium 执行主要用户端到端流程。
5. 使用 JMeter 按冒烟、基准、负载、压力、稳定性顺序测试。
6. 使用 ZAP 扫描并人工复核安全问题。
7. 在 Chrome、Edge 中执行兼容性和人工探索测试。
8. 汇总报告、缺陷、复测结果并给出是否通过验收的结论。

## 12. 测试结果记录模板

### 12.1 用例执行记录

| 用例编号 | 执行日期 | 实际结果 | 状态 | 证据位置 | 缺陷编号 |
|---|---|---|---|---|---|
| 例：API-AUTH-04 | YYYY-MM-DD | 登录返回 200 且取得 Token | 通过/失败/阻塞 | 报告或截图路径 | 无或 BUG-001 |

状态定义：

- **通过**：实际结果与全部预期结果一致，并有可复核证据。
- **失败**：实际结果与任一预期不一致，已记录缺陷。
- **阻塞**：因环境、账号或依赖不可用而无法执行，不计为通过。
- **未执行**：尚未开始执行。

### 12.2 缺陷记录

| 缺陷编号 | 关联用例 | 问题描述 | 严重程度 | 复现步骤 | 状态 |
|---|---|---|---|---|---|
| BUG-001 | 用例编号 | 实际现象与预期差异 | 致命/严重/一般/提示 | 可重复执行的步骤 | 新建/修复中/待复测/已关闭 |

### 12.3 最终测试报告至少包含

1. 测试环境、代码提交号和测试时间。
2. 各类用例的总数、通过数、失败数、阻塞数和通过率。
3. JUnit、Postman、Selenium、JMeter、ZAP 的原始报告或截图。
4. JaCoCo 覆盖率和 JMeter P95、P99、吞吐量、错误率。
5. 未解决缺陷及其影响。
6. 明确结论：通过验收、有条件通过或不通过。

未经执行的用例不得填写为通过；修复后的缺陷必须执行原用例和相关回归用例后才能关闭。
